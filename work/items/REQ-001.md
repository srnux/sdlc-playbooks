## Context

A new web application is to be created on the architecture set out below. The PO
specified the architecture rather than the product: what the application *does* has not
been said yet, and is not assumed anywhere in this item. See the questions.

### The architecture

| Layer | What it is |
|---|---|
| Repo | pnpm workspace, members `apps/*` + `packages/*`; Node >= 24, pnpm 11 |
| Web | `apps/web` — Next.js 16 App Router, React 19, Tailwind 4, TanStack Query 5, Vitest |
| API | `apps/api` — NestJS 11, global `/api` prefix, request-body validation that strips undeclared properties, Jest + Supertest for end-to-end tests |
| Data | Prisma 6 to PostgreSQL 17, migrations checked into the repository |
| Shared | `packages/shared` — pure TS types/enums/constants, consumed by both as `workspace:*` |
| TS | one `tsconfig.base.json`: `strict`, `NodeNext`, ES2023 |
| Boundary | the web app reaches the API **only** through a Next rewrite of `/api/*` to the API origin, so everything the browser calls is same-origin and the API's port is never addressed from client code |
| Bootstrap | one shared application-setup function used by both the production entry point and the end-to-end tests, so both run an identical pipeline |
| Scripts | one command each for dev (shared watcher + API + web together), build, test, lint, database up/down |

## Acceptance criteria

- [AC-1] On a machine with Node >= 24 and pnpm, a clean checkout reaches a running
  application by following the README alone — install, start the database, start the
  app — with no step the README omits.
- [AC-2] The repository is a single pnpm workspace whose members are `apps/*` and
  `packages/*`, holding a web application, an API service, and a shared package.
- [AC-3] The shared package contains types, enums and constants only and imports no
  framework; the web app and the API each depend on it as `workspace:*`. Changing a
  type there and rebuilding raises a type error in any consumer that no longer matches.
- [AC-4] Every workspace extends one strict TypeScript base config; a full build and a
  full lint each exit 0 across all workspaces.
- [AC-5] The API serves every route under a single `/api` prefix and validates request
  bodies against declared DTOs: properties not declared on the DTO are stripped before
  the handler sees them, and a body failing a declared rule is rejected with a 400
  naming the offending field.
- [AC-6] `GET /api/health` returns 200 with a JSON body identifying the service.
- [AC-7] Browser code never addresses the API's port. The web app forwards `/api/*`
  from its own origin to the API; `GET <web-origin>/api/health` returns the API's
  response, and the API's port appears in no client bundle.
- [AC-8] Persistence is PostgreSQL reached through a schema-first ORM whose migrations
  are checked into the repository; applying them to an empty database produces the full
  schema with no hand-written SQL.
- [AC-9] The web app routes through a file-based router with route groups, and fetches
  all server data through a query layer with explicit cache keys and explicit
  invalidation on write — no component performs its own uncached fetch.
- [AC-10] One command starts the shared-package watcher, the API and the web app
  together and reports the port each listens on.
- [AC-11] One command runs every workspace's test suite and exits 0. The API's
  end-to-end tests boot the application through the same bootstrap path production
  uses, so a change to that path is caught by the tests.
- [AC-12] Starting the local database is one documented command and stopping it is one
  more; neither requires a connection detail that is not in the repository.
- [AC-13] If a required environment variable is absent, the affected service fails to
  start with a message naming the variable — it does not start and then fail at the
  first request that needs it.

## Out of scope

- **Every product feature.** No domain has been described yet. This requirement
  delivers the skeleton features would be built in, and no feature.
- **Authentication, authorisation and roles.** Nobody has said who the users of this
  application are, so no auth scheme is assumed. Raised as a question rather than
  guessed at. The same-origin boundary in AC-7 is kept regardless — it is cheap now and
  expensive to retrofit, and a cookie-based scheme later would depend on it.
- **Production deployment and containers.** Separate requirement; it can be specified,
  approved and shipped after this one without changing it.
- **Internationalisation.** Whether the application is multilingual is a product
  decision nobody has taken; see the questions.
- **File uploads and image processing.** Storing user files is a feature, not
  architecture.
- **Demo seed data.** Depends on a domain that does not exist yet.

Open questions. None of these are guessed at above; each would change what gets built.

- **Q1 — What is the application?** The blocking one. This requirement says how to build
  it and nothing about what it does: no user, no domain, no screen.
  `sdlc.config.json → product.name` is still `CHANGE-ME`. The downstream flow — design
  system, prototype, stories — cannot start from an architecture alone.
- **Q2 — Where does it live?** A new repository, or inside this one? This repo currently
  holds only the `.claude` procedure. If the app lands here,
  `sdlc.config.json → verify.commands` (`npm run lint`, `npm test`) is wrong — the
  architecture above is pnpm — and must change with it.
- **Q3 — Does this application need authentication?** If yes, what scheme, and are there
  roles that change what a user can see? If no, say so — it settles a large part of the
  shape of both the API and the route groups in AC-9.
- **Q4 — Pin these versions, or take latest at build time?** The table names Next.js 16,
  React 19, NestJS 11, Prisma 6, PostgreSQL 17, Node >= 24, pnpm 11. Worth deciding
  deliberately: Next.js 16 is recent enough that its conventions differ from most
  published examples and from model training data, so "latest" and "the version that was
  meant" can quietly diverge.
- **Q5 — Multilingual?** If yes, which locales, and which is the source of truth for
  copy? The answer decides whether an i18n library belongs in the web stack at all.
- **Q6 — Does this application adopt the SDLC's token discipline?** The procedure in
  this repo requires a locked `design-system/tokens.css` and forbids raw colours and
  spacing values (`check-tokens.mjs`). Tailwind and that discipline are compatible but
  not identical, and `designSystem.source.ref` is still the placeholder — so where do
  the tokens come from?
- **Q7 — How does a scaffolding requirement travel through this flow?** The coverage
  chain is requirement → screen → story → plan → code, and this requirement has no
  user-facing screen. `check-coverage.mjs` is content at `specified` (verified — it only
  inspects screens once a snapshot is approved), but `approve.mjs` exits 2 on a
  prototype carrying no `data-screen` marker, and `prototypeApprovedBeforeStories` is
  on. So this requirement can be specified but cannot currently reach `approved`, and no
  story can be cut from it. Either scaffolding requirements get an exemption, or the PO
  wants a screen to anchor it to — a landing or health page would do. Needs a decision
  before `/prototype`.
- **Q8 — Is AC-13 wanted in the application itself?** Required-variable checks are
  commonly left to the orchestration layer, which catches them only for containerised
  runs. Enforcing it at start-up is cheap and is the difference between a clear boot
  failure and a confusing 500 much later. Confirm or drop.
