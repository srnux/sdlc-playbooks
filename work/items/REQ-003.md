## Context

The PO's words, verbatim:

> landing page needs to be created. Use attached html mockup `docs/seaside-zadar-v3.html`

The mockup is a public marketing page for a seaside holiday apartment on the Adriatic
coast near Zadar, Croatia. Its job is to make a visitor want the apartment and then get
them to enquire. In the order it draws them, it has: a brand bar that is transparent over
the hero and turns solid on scroll; a full-bleed hero photograph with a headline and one
call to action; a booking bar overlapping the hero; a four-photograph strip; a welcome
paragraph; a four-item facts row (bedrooms, guests, sea view, climate control); an
eight-photograph gallery in which any photograph opens full size with next/previous; a
split location panel; a reservations call to action; and a footer.

### What the PO has since settled

- **The application is a holiday-rental site**, and this page is its first user-facing
  screen. That answers the blocking question on REQ-001, and it is the screen that anchors
  both REQ-001 and REQ-002 in the coverage chain.
- **This page is built inside the REQ-001 monorepo**, as the first route of its web
  application. REQ-001 and REQ-002 are therefore this project's foundation, and this
  requirement depends on REQ-001 for something to build in.
- **The booking bar becomes a real enquiry starter.** Its dates and guest count are
  entered by the visitor and carried into the enquiry. It does not search availability.
- **English only, for now.** One page, one copy set — but the copy is not to be welded
  into the markup, because a second language later should be work, not a rebuild.

### The mockup is the design-system source

Verified, not assumed: `docs/seaside-zadar-v3.html` is **byte-identical** (sha1
`47741f63...`) to `design-system/vinjerac-design-system/seaside-zadar-v3.html`, the canvas
that `design-system/tokens.css` and `design-system/components.md` were locked from, and
which commit `05561c1` deleted from the repository.

The consequence is the useful part: **this mockup asks for no design that is not already
tokenised.** Every colour, size, space and shadow in it is already a `--ds-*` token, and
every element in it is already a catalog entry. Reproducing it is not a design-system
change. What the mockup *omits* -- see the questions -- is.

## Acceptance criteria

- [AC-1] The page presents the mockup's sections, in the mockup's order. A reviewer
  holding the mockup and the page side by side finds no section present in one and
  absent from the other.
- [AC-2] No colour, radius, shadow, font-size or spacing value in the page is a literal;
  each reads a `--ds-*` token from the locked `design-system/tokens.css`.
  `tools/check-tokens.mjs` exits 0 against it.
- [AC-3] The brand bar is legible at every scroll position: over the hero photograph and
  over page content alike, the brand and its links meet 4.5:1 against whatever is
  behind them.
- [AC-4] Every navigation link and every in-page call to action leads somewhere that
  exists. Following each one in turn leaves no dead link and no destination that is not
  on the page.
- [AC-5] Any photograph in the gallery can be opened full size. From there the visitor
  can reach the next photograph, the previous one, and the page again, and can see which
  photograph of how many is being shown.
- [AC-6] The whole page is operable by keyboard alone: every interactive element is
  reachable in the page's reading order and shows a visible focus indicator, the
  full-size photograph view can be entered, moved through and left without a pointer, and
  leaving it returns focus to the photograph that opened it.
- [AC-7] If a photograph fails to load, the section holding it still renders and its text
  stays legible. No section renders as white text on white, and none collapses to zero
  height.
- [AC-8] On a throttled connection the page's text is readable before the photographs
  have finished arriving, and each image's space is reserved at its final size -- sections
  below do not jump as images load.
- [AC-9] At 375px, 768px and 1440px wide the page never scrolls horizontally and no
  section's content is clipped by the viewport.
- [AC-10] At any width where the brand bar's links are not shown, every destination those
  links point to is still reachable from the top of the page without scrolling the whole
  page to hunt for it.
- [AC-11] The booking bar takes real input: the visitor can set an arrival date, a
  departure date and a number of guests, and can see what they have set. A departure date
  earlier than the arrival date, or an arrival date in the past, is refused at the point
  of entry with a message saying what is wrong -- the visitor does not discover it after
  submitting.
- [AC-12] Acting on the booking bar starts an enquiry that already carries the dates and
  guest count the visitor entered. They do not retype any of it, and they do not have to
  copy an address by hand. **The address itself is unknown -- see Q4.**
- [AC-13] Every interactive element carries a stable `data-testid` that is derived from
  neither its copy, nor its class names, nor its position in the DOM.
- [AC-14] Every photograph carries alternative text describing what it shows, and the
  page's headings form a single ordered outline with exactly one first-level heading.
- [AC-15] A visitor is never left unsure whether their enquiry went anywhere. Having sent
  one, they see either a confirmation that it was sent or a plain statement that it has
  been handed to their own mail client -- and if sending fails, what they entered is still
  on screen and they are told how to reach the property another way.
- [AC-16] No visitor-facing string is welded into the markup. Every piece of copy on the
  page is sourced from one place that can be swapped wholesale, so adding a second
  language later is authoring work and not a rebuild.
- [AC-17] The booking bar's Search action does not describe itself as searching
  availability, which the page cannot do. Its label names what actually happens.

## Out of scope

- **A working availability search.** Choosing dates and getting an answer about whether
  the apartment is free needs a source of availability that does not exist. AC-11 and
  AC-12 capture the visitor's dates and hand them to a human; nothing here checks them.
- **Prices, an availability calendar, payment, and reviews.** None appears in the mockup
  and none was asked for.
- **A second language.** English only, by decision. AC-16 keeps the door open; it does not
  walk through it. The locales, the switch control, and the translated copy are a separate
  requirement whenever the PO wants them.
- **Any second page.** House rules, terms, privacy, an imprint, an about page: this
  requirement is the landing page. See Q9 -- an EU-facing rental site may not get to skip
  all of these, but that is someone's requirement to write, not this one's to assume.
- **Search-engine metadata, social sharing cards and structured data.** The mockup has
  none. Deliberately left out rather than invented -- see Q7.
- **Analytics, conversion tracking and cookie consent.** See Q9.
- **Storing enquiries.** Whether an enquiry is persisted, queued or merely sent is part of
  Q4 and is not assumed here. If enquiries need to be recorded and worked through, that is
  an admin requirement nobody has written.
- **Editing the copy or the photographs without a deploy.** No CMS, no admin.
- **Changing the design system.** Tokens and catalog are locked. Everything this page
  needs that they do not have is listed in Q2 and belongs at `/design-system`.

### Open questions

Ordered by what it costs to get wrong. Answered ones are kept, marked, so the reasoning
behind the shape of this item stays readable.

- **Q1 -- ANSWERED. What is the application, and where does this page live?**
  A holiday-rental site, and this page is the first route of the web application in
  REQ-001. So REQ-001 and REQ-002 are this project's foundation, this requirement depends
  on REQ-001 for something to build in, and REQ-001 Q7 and REQ-002 Q7 -- both asking for a
  screen to anchor a screenless requirement -- are answered by this page.
  *Consequence still to be picked up on REQ-001:* its Q3 (does this application need
  authentication?) is now easier. A public marketing page has no users to authenticate.
  If the site never grows an owner-facing side, the answer is no.

- **Q2 -- BLOCKING. Six gaps in the locked design system, and `/design-system` has to
  close them before `/prototype`.** Each is a design decision, and `prototype-rules.md`
  forbids the prototyper improvising any of them:
  - *Gap #4 -- no form controls of any kind.* Now the hard blocker, not just the biggest.
    The booking bar needs a date input, a guest selector, a validation message paired to a
    field, and a disabled state. **AC-11 cannot be met**, and the catalog has no input,
    select, date picker or error-message pattern to build one from.
  - *Gap #7 -- no loading, error or success treatment, and no `--ds-color-danger` or
    `--ds-color-success`.* **AC-15 cannot be met**, and AC-7 and AC-8 have nothing to
    render with. The tokens were deliberately not invented at lock time; they have to be
    decided now.
  - *Gap #2 -- no focus-visible state or token, anywhere.* **AC-6 cannot be met.** The
    mockup's full-size photograph view is currently a keyboard trap with no visible ring,
    and a form the keyboard cannot see its way around is worse.
  - *Gap #5 -- no mobile navigation.* Below 639px the mockup sets the nav links to
    `display: none` with nothing replacing them. **AC-10 cannot be met.**
  - *Gap #1 -- the gold fails contrast.* `--ds-color-accent` is 2.24:1 on white at 12px,
    and it carries the welcome, gallery and reservations eyebrows. It passes only on the
    navy panel. Darken it, restrict it, or accept it -- but decide.
  - *Gap #8 -- the gallery grid is hard-coded to exactly eight photographs* via
    `nth-child`. Fewer breaks the layout; more fall outside it. Couples directly to Q5.

- **Q3 -- ANSWERED. What should the booking bar do?** Start an enquiry carrying the
  visitor's dates and guest count. It does not search availability.
  *Two consequences the prototyper needs:* the bar's button cannot keep saying "Search"
  (AC-17), and the reservations call to action at the foot of the page now overlaps with
  it -- two routes to the same enquiry. Whether they are one flow or two deliberately
  different entry points is a design question for `/prototype`, not a requirement.

- **Q4 -- Where does an enquiry actually go?** Two parts, and the first is now open in a
  way it was not before. *The mechanism:* the mockup uses `mailto:`, which needs no
  backend but hands the visitor off, cannot be confirmed, and is why AC-15 has to accept
  "handed to your mail client" as an outcome. Now that this page lives inside REQ-001 --
  which has a NestJS API and a database -- a real submission with a real confirmation is
  available and was not before. Worth choosing deliberately: a mailto is hours of work, an
  endpoint is days, and only one of them can tell the visitor their enquiry arrived.
  *The address:* `booking@example.com` is a placeholder and `coding-standards.md` forbids
  inventing the replacement. What is the actual address, and is there a phone or messaging
  channel that should sit beside it -- which AC-15 needs for its failure path?

- **Q5 -- The photographs: which ones, from where, at what size?** The mockup embeds eight
  as roughly 4MB of inline base64, which is not shippable as-is -- AC-8 fails on it before
  anything else does. The originals were WhatsApp images dated March--May 2026, deleted
  from the repository in commit `05561c1` and recoverable from git history. So: is this
  the final set of eight (Gap #8 makes the count structural), who produces optimised and
  correctly sized versions, and are there rights or credits to record?

- **Q6 -- What is the property actually called, and are its stated facts true?** The
  mockup's brand reads "Seaside Zadar", the design system is titled "Vinjerac / Seaside
  Zadar", `product.name` is `CHANGE-ME`, and commit `05561c1` removed this very canvas
  describing it as a "test design system ... from other project" before it was re-attached
  here. Which is the name? And separately: are "2 bedrooms", "4+ guests", "180 degree sea
  view", "A/C", and the welcome and location copy the property owner's real, final words
  -- or placeholder prose to be rewritten before this is public? AC-1 reproduces whatever
  is there; it cannot tell true from placeholder.

- **Q7 -- Is being found and shared in scope?** The mockup carries no meta description, no
  social sharing card, and no structured data. For a page whose entire job is to attract
  strangers, that is a real omission -- a link to it pasted into WhatsApp or Facebook today
  would preview as a bare URL. Left out of the criteria above rather than invented. In or
  out?

- **Q8 -- ANSWERED. One language or several?** English only, for now. AC-16 keeps the copy
  extractable so a second language is authoring work rather than a rebuild. Note that this
  is the cheapest start and not the safest one: a Croatian holiday rental draws a
  substantially German, Italian and Polish audience, so the second language is a question
  of when, not whether.

- **Q9 -- What does a public, EU-facing page have to carry?** Three related decisions all
  currently out of scope: analytics and conversion tracking (and, if any, a consent
  mechanism); an imprint and a privacy notice, which a commercial rental site aimed at EU
  visitors would normally need; and the accessibility conformance target. Two of these got
  heavier when the booking bar became a form: an enquiry collects personal data, so a
  privacy notice stops being merely advisable, and a form is where accessibility
  conformance is actually tested. Say which of these matter and each becomes a
  requirement; say none do and they are out of scope deliberately rather than by omission.

- **Q10 -- Housekeeping, cheap now.** `designSystem.source.ref` in `sdlc.config.json` is
  still `INPUT_YOUR_ARTIFACT_URL_OR_FILE_PATH_HERE`, and `tokens.css` says it derives from
  `design-system/vinjerac-design-system/seaside-zadar-v3.html`, a path commit `05561c1`
  deleted. The identical file now sits at `docs/seaside-zadar-v3.html` -- which is
  `artifacts.docsDir`, the engineer's output directory, so it is liable to be mistaken for
  a generated document. Give the canvas a stable home and point the config at it, or the
  next `/design-system` run has no source to re-lock from. Also: `verify.commands` is
  still `npm run lint` / `npm test`, which is wrong now that this page is confirmed to
  live in a pnpm workspace (REQ-001 Q2 raised this; the stack answer settles it).
