## Context

The architecture the PO specified covers how the application is *run*, not only how it
is built: a production-like container stack on a single host — database, API, and the
web app as a standalone build — reached on one published port, with named volumes for
state and schema migrations applied automatically on API start.

This is separated from the foundation requirement because it can be specified, approved
and shipped on its own, later, without changing anything in that one. Development does
not wait on it.

### The deployment shape

- Three services: PostgreSQL 17 with a readiness healthcheck, the API, and the web app.
  Only the web service publishes a port to the host.
- The web container reaches the API over the internal container network, at an address
  fixed at image-build time. Nothing outside the network talks to the API.
- Named volumes carry database state (and any file storage, if it turns out to be
  needed) across container replacement.
- Configuration and secrets come from an environment file copied from a checked-in
  example; the stack refuses to start when a required value is unset.
- The web app builds in standalone mode with its file-tracing root at the monorepo root,
  so its image carries only what that workspace needs rather than the whole repo.

## Acceptance criteria

- [AC-1] From a clean checkout with no toolchain beyond Docker, copying the example
  environment file, filling in the required values, building and starting the stack
  reaches a working application — with no step the README omits.
- [AC-2] Exactly one service publishes a port to the host. A request to that port
  reaches the web application, and the API and the database are not reachable from the
  host on any port.
- [AC-3] The web container reaches the API over the internal container network only;
  the internal address appears in no response sent to a browser.
- [AC-4] Database schema migrations are applied automatically when the API container
  starts, against whatever state the database is in; starting the stack a second time
  applies nothing and does not fail.
- [AC-5] Database state survives a stop followed by a start — data written before the
  stop is present after the start. Data is held in a named volume, not in a container
  layer.
- [AC-6] If a required secret or environment variable is unset, the stack refuses to
  start with a message naming the variable. It does not start with a default or empty
  value.
- [AC-7] Each image contains only the workspace it serves plus that workspace's
  dependencies — not the whole monorepo, and no development-only dependencies.
- [AC-8] The web application's production build happens during the image build, and the
  build fails the image if type-checking or linting fails.
- [AC-9] The database container reports healthy before the API container starts, and the
  API does not crash-loop on a database that is still starting up.
- [AC-10] The README gives the deployment commands and names every value that must be
  set before the first start.

## Out of scope

- **Any hosting platform beyond a single host running containers.** Kubernetes, ECS, a
  PaaS, or a managed database are all different requirements. Nothing here assumes more
  than one host.
- **TLS, domains and reverse proxying.** What terminates TLS is not specified here — see
  the questions.
- **CI/CD.** Nothing in this requirement builds or deploys these images automatically.
- **Backups, restore and retention** for the database volume. Named volumes persist;
  they are not a backup. Raised as a question.
- **Monitoring, log aggregation and alerting.**
- **Horizontal scaling.** One instance of each service.

Open questions. None of these are guessed at above.

- **Q1 — Where does this actually run?** A developer's machine, an internal server, or
  something public? The answer decides whether AC-2's single published port is the whole
  story or the start of one.
- **Q2 — Who terminates TLS?** If this is ever reachable from outside a trusted network,
  something in front must. If a cookie-based auth scheme is chosen (REQ-001 Q3), its
  `secure` flag depends on this answer. If the target is a private network only, say so
  — then it is out of scope deliberately rather than by omission.
- **Q3 — Where do secrets come from?** An environment file on the host is the assumed
  default. Is that acceptable here, or is there a secret store this should read from?
- **Q4 — Is a file-storage volume needed at all?** Whether this application stores user
  files is a product question that is not answered yet — see REQ-001 Q1. If it does not,
  the volume comes out.
- **Q5 — Who backs up the database?** AC-5 covers restart survival, which is not the
  same as surviving a lost host. If backups matter, they are a requirement someone has
  to write.
- **Q6 — Is a demo-data seed wanted in the deployed stack?** Depends on a domain that
  does not exist yet.
- **Q7 — Does this requirement need a screen?** As with REQ-001, this one has no
  user-facing screen, and `approve.mjs` refuses a prototype without a `data-screen`
  marker — so it can be specified but not approved, and no story can be cut from it.
  Needs the same decision as REQ-001 Q7.
